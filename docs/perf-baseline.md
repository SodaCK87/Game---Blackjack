### 量測方法（下一輪要能比，就照這幾條）

1. 頁面內的分段計時由 CDP 在頁面載入前注入，只包外層函式（render、引擎、勝率、貼圖、牌桌與佈景建立、resize），`app\` 一個字沒改。陽性對照 ✅：在暫存複本把 render 的埋點弄斷，4 筆輸出都報「埋點沒接上 render」。
2. 每一局用固定種子（凍結 `Date.now`），所以 5 次量的都是同一副牌、同一串事件；一律按停牌，要牌與加倍的路徑沒有單獨量。
3. 「按下到下一格畫面」是從 click 到下一個 requestAnimationFrame。「長掉格」是瀏覽器的 Long Animation Frame（超過 50 ms 的一格）。陽性對照 ✅：在一格裡故意忙 120 ms，觀察器記到 126 ms。
4. 一局裡的「其他主緒工作」是 CDP TaskDuration 扣掉所有埋點，「主緒閒著」是總時間扣掉兩者。⚠️ TaskDuration 的窗口尾巴比該段長一點（對白泡泡還在飄），兩欄的數字是近似。
5. 連玩：加速 40 倍，每 50 局 GC 後量一次 heap；量之前先清掉埋點自己記的資料。✅ 同一種子沒清時每 50 局漲約 1 MB，清了之後第 50 局起每 50 局只漲約 0.1 MB。
6. 無頭 Edge 加了 `--disable-extensions --disable-sync`，並自己開分頁、關掉其他分頁。⚠️ 這台的 Edge 連全新設定檔都會開擴充頁與同步確認頁、把量測分頁擠成 hidden，動畫就停了（前段冒煙實測）。所以這裡的數字不含同事瀏覽器上擴充的影響。
7. 本輪同時跑了一支觀察腳本，每 3 秒查一次所有無頭瀏覽器的分頁清單：486 個設定檔裡，`tests\browser_util.js` 開的 Edge 出現 1 次 `edge://sync-confirmation-dialog/`；claude.ai 的 OAuth 頁沒有再出現。⚠️ 3 秒以內開了又關的分頁可能漏掉。
8. `npm test` 的分段是 node 測試報表（junit）裡每支檔的測試本體時間。各檔平行跑，所以佔比用各檔加總當分母；總計是牆鐘時間，比打 `npm test` 少了 npm 自己啟動的約 0.35 秒。
9. 「推上 main 到 Pages 發布完」是 GitHub 記的歷史值（最近 3 次成功的 workflow），不是本腳本量的。

### 建議先做的

全部入口都在使用者門檻內，沒有一項必須做。要做的話照「等待時間 × 頻率」排：

1. P-10，再做 P-09：開發者每改一次就要等 2.5 分鐘的 npm test，這兩項直接縮短關鍵路徑。P-10 的改動也會讓 shoot.js 與 check_live.js 一起變快。
2. P-01：每位同事每次開頁都會等到，佔冷開一半以上。可是整段才 1.0–1.3 秒，在 3 秒門檻內，只有想讓開頁更快時才做。
3. P-11：mutants 從 22.7 秒往下砍，改測試迴圈就好，可以不動 core。
4. P-06：不縮短任何等待，省的是手機電。真手機實測時如果發燙或掉格，再提前做。

### 不值得做

1. 開網址的 HTML 下載（132–152 ms，10.3–11.5%）：是 GitHub Pages 的網路來回，程式改不動。
2. 冷開時建 WebGLRenderer（130–136 ms，13.3–13.9%）：只有剛啟動的無頭瀏覽器第一次才這麼久，重新整理時 8.4–8.6 ms、開網址時 12.7–20.3 ms。📌 推測是 GPU 行程剛啟動；同事的瀏覽器通常本來就開著。
3. 一局裡的「主緒閒著」（44.5–57.1%）：這是設計好的動畫節奏，使用者說只管卡頓、不管節奏。
4. 一局裡的引擎、勝率計算、標籤夾回畫面、貼圖現畫：每段各 ≤0.1%；瀏覽器內勝率一次 0.2–0.6 ms，node 裡一次 0.07 ms。
5. 一局裡的 render 直接呼叫（換表情、亮圈）：0.3–0.9%。
6. 開頁的 core 6 支、view 11 支載入、佈景、荷官建立、導演建立、光點擺位、core 自測一局：各 <2%。
7. 轉向的 resize 監聽器（中位 5.6–6.3 ms、最大 14.3 ms）與下注列按鈕（4.6–5.2 ms）：最大值離 0.1 秒門檻也還有 7 倍。
8. build:three（401 ms）：只在升級 three 時跑。
9. mutants 其他 13 個破壞：各 1.0–2.6%。
10. check_three_bundle、check_odds（各 0.5%）與其餘 core 測試檔（各 <0.1%）：不在關鍵路徑上。
11. Pages 發布（中位 49 秒）：GitHub 端的時間，這個 repo 改不動。
12. check_live.js 與 shoot.js 的各個分段：每段的成本就是 P-10 加上一次開頁（P-01），跟著那兩項一起處理。

### 量不到的部分

1. 真手機的 CPU 與 GPU：這裡的手機只模擬尺寸與 DPR2，跑的還是這台筆電，數字偏樂觀。替代：使用者用真手機開網址手動計時到可下注，再玩一局看有沒有卡；或之後在腳本加 CPU 節流模擬（還沒做）。
2. GPU 實際作畫的時間：render 只量到 JS 送出指令的時間。
3. 同事瀏覽器裝了擴充時的情形：量測刻意關掉擴充（〈量測方法〉第 6 條）。

### 建議先做的

1. P-14：玩家端唯一超過使用者門檻的一項，每次開頁後的第一個 Blackjack、每一次加倍都會碰到。先在量測腳本把開場那一格拆開，再決定改哪裡；P-13 可能一起改。
2. P-09，接著 P-10：`npm test` 連沒失敗的那兩次都要 5.2 分鐘，超過門檻。P-10 也會讓 `shoot.js` 與 `check_live.js` 一起變快。
3. P-11：mutants 從 22.7 秒變 82 秒，其中約六成是 `check_simulation.js` 那三個破壞加基準；只改測試迴圈就好，可以不動 core。
4. P-13 加 P-06：不縮短任何等待，省的是手機電；如果 P-14 拆開後發現重畫佔了那一格，就提前做。

### 不值得做

1. 開網址的 HTML 下載（134–195 ms，8.7–10.9%）：是 GitHub Pages 的網路來回，程式改不動。
2. 冷開時建 WebGLRenderer（145–163 ms，12.9–14.5%）：只有剛啟動的瀏覽器第一次才這麼久，重新整理時 9.0–10.2 ms。
3. 一局裡的「主緒閒著」（44.1–52.2%）與大特效的「主緒閒著」（16.8–36.7%）：設計好的動畫節奏。
4. 分牌那一局「按分牌到輪到第 1 手」1,398–1,411 ms（9.7–9.8%）、加倍那一局比沒特效的多 3.1 秒：佔比過 5%，但都是設計好的動畫，使用者說總長不設上限。
5. 開頁後第一段大特效的開場同步工作 47.4／67.7（桌機）、56.3／77.7（手機），佔該段 2.3–2.7%：它落在 P-14 的那一格裡，跟著 P-14 一起處理；之後幾段只剩 5.6–11.0 ms。
6. 大特效比設計長度多出 12.6–64.7 ms（0.6–3.2%）：等的是最後一格畫面。
7. 一局裡的引擎、勝率、標籤、貼圖現畫（各 ≤0.1%）與 render 直接呼叫（0.3–1.0%）；瀏覽器內勝率一次 0.2–0.7 ms，node 裡含分牌的一次 0.30 ms。`director.js:216-217` 每次 `updateLabels` 都深拷貝一次狀態，也在這一桶裡。
8. 開頁的 core、view 載入、佈景、荷官建立、導演建立、光點擺位、core 自測一局：各 <2%。
9. 轉向（中位 5.8–6.1、最大 13.8）與下注列按鈕（5.0–5.2）：最大值離 0.1 秒還有 7 倍。
10. build:three（399 ms）：只在升級 three 時跑。
11. mutants 其餘 57 個破壞：各 0.2–1.9%。
12. `check_odds.js`（1.0%）、`check_three_bundle.js`（0.4%）與其餘 core 測試檔（各 <0.1%）：不在關鍵路徑上。
13. Pages 發布（中位 44 秒）：GitHub 端的時間。
14. `check_live.js` 與 `shoot.js` 的各分段：每段的成本就是 P-10 加上一次開頁（P-01）。
15. 連玩時畫面疊字元素 4→16：不是洩漏，`director.js:183-187` 的點數標籤照「這個座位最多分過幾手」建好就重用，有上限。

### 量不到的部分

1. 真手機的 CPU 與 GPU：手機只模擬尺寸與 DPR2，數字偏樂觀。大特效那層 220vmax 的放射光芒在 DPR2 手機上約 3714 實際像素見方，作畫成本在 GPU 上，主緒量不到。替代：使用者用真手機開網址，拿到 Blackjack、按加倍時看有沒有頓一下。
2. GPU 實際作畫的時間：render 只量到 JS 送出指令的時間。
3. 「開頁後第一段大特效是加倍或荷官 Blackjack」：疊牌順序固定，第一段一定是你拿 Blackjack；加倍的第一次成本沒有單獨量。
4. 「要牌」路徑：分牌那一局兩手都按停牌，要牌仍沒有單獨量。
5. 同事瀏覽器裝了擴充時的情形、Chrome：同第 1 輪。

### 雜訊

1. `npm test`：5 次是 613,256、645,925、458,552、313,352、312,573。前三次（07:16–07:45）每支檔都慢了一倍左右，而且各有一條測試失敗；後兩次沒有失敗、都是 313 秒。📌 前三次變慢的原因沒查到，可能是機器熱節流或背景負載，失敗看起來是變慢造成的逾時，不是失敗拉長了時間（一條失敗最多多 44 秒）。判定不受影響：中位數 7.6 分鐘、沒失敗的 5.2 分鐘，兩者都超過 5 分鐘。
2. fx、oddsplit、live 三段開始前 CPU 26–35%，比其他段的 1–21% 高，原因不明。疊牌那幾局裡有 4 次取樣冒出 8–56 個長掉格（例如手機沒特效那一局第 1、3 次各 8 格、最長 258 ms），連沒有特效的局也有，所以判成環境雜訊。大特效的判定沒受影響：第一段每次 2 格、加倍每次 2–3 格，10 次全中。
3. 開網址手機 5 次裡有 2 次 8,765 與 9,525 ms（第一次 render 3.6–5.2 秒），`check_live.js` 第 4、5 次 58,739 與 74,085 ms：都在這一段，判成環境雜訊；中位數仍在門檻內。
4. mutants 第 5 次 138,303 ms（其他 4 次 81,632–84,250），`check_simulation.js` 那幾個破壞慢了近三倍。
5. 冷開的 FCP、`shoot.js --round`（39,739／78,913，含一次 CDP 逾時）與幾個毫秒級分段的最大值也超過中位數兩倍，絕對值離門檻很遠，或本來就不設門檻。

1. `npm test` 6 次（含 warmup）有 4 次各有一條測試失敗，每次是不同的測試：`check_play.js` 的陽性對照「大特效照真實時間等 2 秒才收」與「導演沒等荷官 Blackjack 的大特效播完」各一次、`check_dealer.js`「chrome：直式手機的長句泡泡」CDP 逾時一次、`check_room.js`「edge・超寬螢幕」一次。全部平行跑時會隨機有一條紅，這是測試可靠度的問題，交給 R01。時間照記，見〈雜訊〉第 1 條。
